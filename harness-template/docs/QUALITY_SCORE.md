# QUALITY_SCORE.md — 품질 평가 가이드

> 구현자가 작업 완료 후 자가 평가하고, 검토자가 코드 리뷰 시 사용하는 체크리스트.
> A·C 전항목은 **필수 통과** 기준. 충돌 시 이 문서가 이긴다.

---

## 사용 시점

1. **구현자**: 작업 완료 후 실행 계획 파일에 결과 기록
2. **검토자**: `/review` 명령 실행 시 이 체크리스트로 평가
3. **테커푸**: 품질 기록 단계에서 간략 점검

---

## 평가 체크리스트

### A. 코드 품질 (필수 — 전항목 통과해야 배포 가능)

- [ ] `{{BUILD_CMD}}` 성공 — 타입 에러 0건
- [ ] 느슨한 타입(`any` 등) 사용 없음
- [ ] 린트 경고/에러 0건
- [ ] 비즈니스 로직이 서비스 클래스/모듈에 캡슐화됨 (라우트 핸들러에 직접 로직 없음)
- [ ] 주석 작성됨 (클래스/메서드 문서화 포함)

### B. 설계 품질

- [ ] 단일 책임 원칙 준수 (클래스/함수가 하나의 역할만)
- [ ] 기존 패턴 일관성 유지
- [ ] 불필요한 복잡도 없음 (더 단순한 방법 있으면 단순한 쪽)
- [ ] 연쇄 반영 완료 (API↔UI, DB↔서비스, i18n, 타입/Props 전파)

### C. 보안 (필수 — 전항목 통과해야 배포 가능)

- [ ] 시크릿/API Key/토큰 평문 노출 없음 (코드·로그·응답 모두)
- [ ] 사용자 외부 입력에 스키마 검증(Zod 등) 적용
- [ ] 에러 응답에 내부 스택/경로 정보 미노출
- [ ] 런타임 호환 (금지 API 미사용 — RELIABILITY.md 참조)

### D. 테스트 가능성

- [ ] 핵심 경로에 에러 처리(try-catch) 존재
- [ ] 비동기/외부 작업에 실행 로그 기록

### E. 문서 동기화

- [ ] `docs/progress.md` 업데이트 (완료 항목 체크)
- [ ] 테스트 레퍼런스 업데이트 (UI 변경 시)
- [ ] i18n 양쪽 반영 (새 문자열 추가 시)

### F. 서비스 품질 (Ship 레벨 기능 필수)

- [ ] 에러 메시지가 사용자 친화적 (raw API 에러·스택 노출 없음, i18n 적용)
- [ ] 비동기 동작에 로딩 인디케이터 존재 (버튼 스피너, 섹션 스켈레톤)
- [ ] 빈 상태에 안내 메시지 + CTA 버튼 존재
- [ ] 복잡한 설정 필드에 도움말/툴팁 존재
- [ ] 파괴적 동작에 확인 모달 존재 (삭제, 연결 해제 등)
- [ ] 성공 피드백 표시 (토스트, 리스트 자동 갱신)
- [ ] 실패 복구 경로 존재 (재시도 버튼)

### G. 디자인 품질 (UI 변경 포함 작업 필수)

> Notion, Linear, Vercel 수준의 정제도를 목표로 한다.

- [ ] **여백 충분** — 요소 간 간격 일정, 꽉 찬 느낌 없음
- [ ] **정보 계층 명확** — 제목 > 설명 > 보조정보의 크기·굵기·색상 차이가 보임
- [ ] **워딩 자연스럽고 프로페셔널** — 기계적 번역 느낌 없음, 톤 통일
- [ ] **컴포넌트 일관성** — 버튼·뱃지·카드 스타일이 기존 페이지와 동일 패턴
- [ ] **기능 완결성** — 진입 경로→실행→결과 확인→복귀 경로가 모두 존재

## 평가 등급

| 등급 | 기준 | 다음 단계 |
|------|------|----------|
| **통과** | A 전항목 + C 전항목 + B 3/4 이상 + E 다수 + F 5/7 이상 + G 4/5 이상 (UI 변경 시) | 테스터로 전환 |
| **조건부 통과** | A 전항목 + C 전항목, B·D·E·F·G 일부 미달 | 사유 기록 후 진행 가능 |
| **미달** | A 또는 C 1건 이상 미달 | 수정 필수, 재평가 |

## 소규모 변경 (S 규모) 축약 체크

1~3개 파일 변경의 경우 실행 계획 없이 아래만 확인:

- [ ] 빌드 성공
- [ ] 보안 이슈 없음
- [ ] 연쇄 반영 누락 없음
